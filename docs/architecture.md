# Architecture and implemented contracts

Status: S0-S6.1 are complete and preserved on main. S7A-S7C and the sidebar refinements are published on feature/javafx-ui, providing all six desktop views and existing booking/lifecycle operations. The addenda below preserve historical implementation stages. See [project status](project-status.md) for release verification, ui-review/S7C.md for presentation behavior and S6-AUDIT.md for historical qualifications.

## Implemented S1/S2 contracts

`domain.model` contains immutable Customer, ServiceProvider, Service, TimeSlot and BookingOptions, typed CustomerId/ProviderId/ServiceId/AppointmentId, Money, WorkingPeriod and the status/mode/kind/category enums. IDs and names are stripped and nonblank; S3 validates customer/provider/service references against immutable injected catalogs and rejects duplicate appointment IDs atomically. Constructor compatibility checks compare the service ID and mode with provider support, not a global catalog lookup.

Money stores nonnegative EUR, validates negativity before rounding (including -0.001), and normalizes to scale 2 HALF_UP. BookingOptions owns an immutable map of normalized add-on codes to fee snapshots, rejects duplicate normalized codes and contains no add-on behavior. Provider collections and nested working periods are copied; working hours must be present, same-day, non-overlapping; preparation buffer is nonnegative configuration consumed by S3 PreparationBufferAvailabilityStrategy.

Appointment in `domain.appointment` is a **sealed abstract immutable aggregate**, with final ConsultationAppointment and ServiceAppointment products. AppointmentBuilder assembles a ValidatedAppointmentSpec and invokes an AppointmentCreator. The specification validates required fields, provider service/mode support, service-derived duration, future start, working hours and base fee. It stores business zone, compatible mode products and an immutable enhancement snapshot. Construction starts PENDING and does not reserve, check global collisions, allocate IDs or publish events.

`confirm(DomainTime)`, `cancel(DomainTime)`, and `complete(DomainTime)` return new Appointment values. The original is unchanged on success and failure; callers must retain the returned value. State is private with no constructor accepting arbitrary state and no public state setter. A sealed AppointmentState interface declares rejecting defaults, with PendingState/ConfirmedState overriding permitted behavior; CompletedState/CancelledState inherit terminal rejection. Each invocation captures one injected current instant. Invalid status operations throw InvalidTransitionException; data/time-rule violations throw DomainValidationException. There is no lifecycle switch in production code.

`validateReschedule(Instant, DomainTime)` delegates original-slot eligibility to State, checks the new future service-derived interval and working hours, and returns a proposed TimeSlot only. It retains ID, status and slot by never changing the original. Changing the business zone through a proposal is rejected. S3 adds reschedule(Instant, DomainTime), returning a detached same-subtype, same-State appointment with a validated new spec. Only repository reschedule commits it after conflict checks; the proposal API remains unchanged.

`domain.time.DomainTime(Clock)` defaults to Europe/Vilnius; `(String zoneId, Clock)` allows explicit configuration independent of the Clock zone. `resolve(LocalDateTime)` returns a ZonedDateTime with the selected offset visible, rejects gaps and chooses the earlier Instant in overlaps. `now()` delegates to the injected Clock. Main reads appointease.zone and injects the configured zone and Clock.

S2 replaced direct Appointment construction. Existing S1 test assertions are retained through a fixture helper using Builder and creators. Lifecycle copies preserve concrete subtype, identity, mode family and enhancement snapshot. Atomic persistence below is implemented in S3; event/revision and delivery contracts below are implemented in S4.

## Layers and dependency direction

| Package under com.appointease | Ownership and allowed project dependencies |
| --- | --- |
| domain.model, domain.appointment, domain.creation, domain.mode, domain.scheduling, domain.state, domain.event, domain.addon | Entities, validation, creation, families, policies, lifecycle, events, composition. Domain depends only on domain and Java standard APIs. |
| application, application.port, application.event | BookingFacade, CommittedEventDispatcher, request/result records, event publisher/listeners, use cases, repository and CalendarPort abstractions. Depends on domain, never presentation/infrastructure. |
| infrastructure.memory, infrastructure.calendar, infrastructure.notification, infrastructure.seed | Implements application ports and application listeners; depends on application/domain. |
| presentation | Console parsing/rendering; depends on application contracts and domain values needed for display; no repository access. |
| Main (root) | Sole composition root; constructs Clock, zone, repositories, adapter, listeners, creators, policies, decorators, facade, console. May reference every layer. |

These are compile-time import rules, initially a review constraint in one Maven module; S6 added ArchitectureTest using JDK jdeps on compiled classes and reflection checks for static fields. No domain port is forced into application if the domain itself needs that abstraction. Application code receives CalendarPort through its constructor, never constructs ExternalCalendarAdapter. No DI framework, singleton container or cyclic constructor injection is used. S6.1 eliminates all four intra-layer package cycles. `domain.model` holds shared values/catalog data; `domain.appointment` owns Appointment, its two products, ValidatedAppointmentSpec and AppointmentRules and depends on model/state/mode/addon/time/exception. State, mode and addon depend on shared model values, never the aggregate. `application.CommittedEventDispatcher` owns command coordination/receipts and depends on event publishing contracts; application.event no longer depends on application orchestration. All 19 production packages form an acyclic graph. See S6-AUDIT.md for original cycle edges and migration rationale.

## Entities and value APIs

The following table summarizes implemented types and invariants; exact signatures are in source. Collections are defensive immutable copies. IDs use dedicated records wrapping nonblank String values; generated IDs use UUID strings, deterministic IDs use reserved seed prefixes. Generated IDs use UUID; duplicate insertion rejects. Automatic UUID collision retry is not implemented.

| Type | Implemented API / invariants / ownership |
| --- | --- |
| Customer | Immutable Customer(CustomerId, name); nonblank name. Owns identity only; history is queried, not a mutable embedded list. |
| ServiceProvider | Immutable ProviderId, name, category, supported ServiceIds, supported modes, weekly working hours, preparation Duration >= 0. Catalog owns it. |
| Service | Immutable ServiceId, name, positive Duration, EUR base fee, AppointmentKind. Shared catalog value referenced by providers and appointment snapshots. |
| TimeSlot | Immutable TimeSlot(Instant start, Instant end); start < end; overlaps(other). No mutable Date or local timestamp persistence. |
| BookingOptions | Immutable selected add-on codes and fee breakdown snapshot; no duplicated priority/reminder behavior flags. Reject duplicate add-ons; decorator chain drives behavior. |
| Appointment | Implemented sealed abstract aggregate with ConsultationAppointment and ServiceAppointment products and compatible mode components. Lifecycle operations continue to return validated immutable replacements, with no public setters. |
| AppointmentMode | Enum ONLINE, IN_PERSON; family discriminator, not lifecycle behavior. |
| AppointmentStatus | Enum PENDING, CONFIRMED, COMPLETED, CANCELLED for queries/events; behavior belongs to AppointmentState. |
| AppointmentEvent | Immutable String event ID, global sequence, revision, event type, occurredAt Instant, before/after snapshots (before absent for reserve); reschedule includes old/new slot. No live aggregate reference. |

Appointment is the lifecycle consistency boundary. The S3 repository owns immutable Reservation records (Appointment plus preparation Duration); callers receive immutable Appointment/Reservation values directly. A separate AppointmentView is unnecessary at this stage. Transitions under the lock construct immutable replacements and expose them only on success. Customer/provider/service cannot be silently modified through an appointment. S4 appointment revision begins at 1 for reserve and increments once per successful committed operation, stored with the event under the repository lock.

## Creation and optional services

AppointmentBuilder gathers ID, customer, provider, service, start or explicit TimeSlot, mode family and an AppointmentService component (base by default). The last start/slot setter wins; explicit slots must equal the service-derived duration. build(AppointmentCreator, DomainTime) quotes the service, constructs a fully validated domain.appointment.ValidatedAppointmentSpec, then invokes the creator template. Each build revalidates against the injected time. Builders are mutable, local assembly objects and are not thread-safe; appointments and snapshots are immutable.

ValidatedAppointmentSpec has a public, fully validating constructor; final subtype constructors accept only this validated value and enforce their own kind. This refines the originally planned restricted-constructor API: validation remains unavoidable, while the model does not depend on creation orchestration. AppointmentCreator.create(spec) checks service kind before calling protected abstract createAppointment(spec). The two concrete overrides instantiate distinct products. AppointmentRules holds the S1 slot checks shared by creation and reschedule proposals. A spec is a point-in-time validated candidate, never a reservation; S3 rechecks current time and availability under the store lock.

AppointmentModeFactory creates MeetingDetails and ParticipationInstructions. OnlineModeFactory produces simulated meeting/join text; InPersonModeFactory produces location/reception text. Each immutable factory instance owns a private identity shared by its products. AppointmentModeDetails rejects different modes or identities, including two online sessions with identical labels. The sealed product interfaces permit only immutable family records; clients use the interfaces. A future new mode requires explicitly extending the sealed family. No meeting URL or external session is provisioned.

AppointmentService.quote(Service) returns immutable BookingEnhancements (base EUR fee, BookingOptions, ordered instruction strings). No separate BookingContext is needed in S2. BaseAppointmentService quotes the catalog fee; it can also import an existing fee snapshot without inventing instructions. AppointmentServiceDecorator delegates; PriorityBookingDecorator adds EUR 10.00 and a priority-handling instruction; ReminderServiceDecorator adds EUR 2.00 and a reminder instruction. Constructor-injected Money fees support alternate pricing, using the existing nonnegative scale-2 HALF_UP contract. Duplicate add-on codes fail. Both orders are supported: fees are additive/order-independent, instructions follow inner-to-outer delegation order. No notification is sent and no priority scheduling override exists.

Builder stores the quote in the validated specification; base fee must equal the service fee. State replacements share this immutable snapshot. Decorators never receive or mutate an Appointment, so they cannot change identity, date, provider or status. Instruction strings are currently display/consumer data, not a delivery protocol; Observers retain immutable event snapshots without parsing prose as scheduling policy.

## Availability and atomic storage (implemented S3)

AvailabilityStrategy.preparationBuffer(ServiceProvider) supplies additional preparation restrictions through polymorphic dispatch. StandardAvailabilityStrategy returns zero; PreparationBufferAvailabilityStrategy defaults to the immutable provider configuration or accepts an explicit nonnegative Duration. ReservationRules unconditionally reconstructs a ValidatedAppointmentSpec for intrinsic checks and checks the raw candidate interval against existing effective occupancy before invoking the policy. Policy output cannot shrink the raw interval: null/negative/overflowing buffers fail. This refines the conceptual schedule-assessing strategy into a small preparation-policy contract, with conflict and working-hour enforcement owned by unconditional rules.

Reservation is an immutable appointment plus buffer snapshot. Effective occupancy is [start-buffer, end), must fit a single working interval, and cannot overlap another occupying reservation for the same provider. Preparation may begin before the transaction time; the appointment itself must start strictly after it. Completed reservations retain their effective interval; cancelled reservations release it. A later standard booking still respects every prior buffer snapshot. Strategies are not retained. Custom policies should be quick, pure and must not wait for another repository command; they execute inside the store lock.

Application-owned AppointmentRepository exposes find(AppointmentId), history(CustomerId), reservations(), reserve(candidate, strategy), reschedule(id, newStart, strategy) and transition(id, AppointmentTransition). No public save/check-then-write API exists. History contains current appointment snapshots in all statuses, sorted by start then ID; it is not an operation/event log. reservations() returns the same deterministic order and immutable policy snapshots. Unknown lookup returns Optional.empty; unknown customer history is empty; commands on missing appointments fail.

InMemoryAppointmentRepository receives collections of customers/providers/services, Clock and ZoneId through its constructor. Catalog collections are defensively copied into immutable ID maps, duplicate catalog IDs rejected. Reserve requires exact catalog value equality (including supported services/modes, hours, duration and fees), rejecting missing or spoofed references. This intentionally implements reference validation without adding unused catalog interfaces, dynamic catalog editing or seed data. IDs are caller-supplied typed values, unique within the repository; insertion never overwrites an existing ID, even if cancelled. New reservations must be PENDING; historical-state import is not supported.

One instance-owned ReentrantLock protects every appointment-map read/write. No provider index is needed for this academic dataset. Each command reads the latest stored value, captures one injected Clock instant under the lock, uses a fixed DomainTime for the entire transaction, constructs and validates detached replacements, then performs one map put. Every failure before put leaves the complete store unchanged; finally releases the lock. Reads return immutable snapshots. Strategies cannot perform nested writes: a reentrancy guard rejects these before mutation, preventing callback-induced snapshot invalidation. No delivery/listener/calendar code runs here.

Reschedule invokes immutable State eligibility and existing slot rules, excludes only its own ID from conflict checks, and replaces the old reservation only after all checks pass. It preserves ID, subtype, status, customer/provider/service, business zone, family, fees and ordered add-on instructions. Its explicit policy parameter replaces the policy snapshot on success. State transitions use the latest stored appointment, delegate to State via finite AppointmentTransition commands, and preserve the buffer. Concurrent confirmation/rescheduling cannot lose either update. There is no arbitrary caller callback for replacing stored aggregates.

S4 extends this transaction with one commit helper: replacement, per-appointment revision and append-only global event log are recorded under the same lock. The event uses the same captured transaction instant. events() returns immutable ordered snapshots. Catalog browsing methods providers()/services() sort by ID; customer(id) resolves the same immutable catalog used for reservations. No calendar/listener callback executes under this lock.

## Lifecycle and errors

| State object | confirm | cancel | complete | reschedule |
| --- | --- | --- | --- | --- |
| PendingState | ConfirmedState | CancelledState | reject | same state, future original/new start |
| ConfirmedState | reject | CancelledState | CompletedState, now >= end | same state, future original/new start |
| CompletedState | reject | reject | reject | reject |
| CancelledState | reject | reject | reject | reject |

Confirm/cancel also require now < original start. Implemented domain methods delegate to AppointmentState rather than switching on status; state returns a permitted next state, aggregate returns an immutable replacement. The S3 repository transaction commits that replacement. S1 uses InvalidTransitionException and DomainValidationException. S3 uses DomainValidationException/InvalidTransitionException for existing rule failures, SlotUnavailableException for occupied capacity, and application RepositoryException with NOT_FOUND, DUPLICATE_ID, CATALOG_MISMATCH or REENTRANT_WRITE reasons. Facade preserves these typed failures; S5 console reports expected errors and returns to the menu. Failed domain operations leave every observable field unchanged.

## Time and money

Inject Clock; do not call Instant.now() or LocalDateTime.now() in business logic. Startup resolves `System.getProperty("appointease.zone", "Europe/Vilnius")` with ZoneId.of and fails clearly on invalid configuration. Provider working hours use this application zone in the first release; no per-provider timezone feature. Clock's zone never silently overrides configured business zone.

Resolve LocalDateTime using zone.getRules().getValidOffsets(local): zero offsets => reject nonexistent DST-local time; one => use it; two => convert each to Instant and choose minimum (earlier occurrence), show chosen offset to user. Never use default atZone normalization for user input. Apply the same rule to dated working-hour boundaries; if a boundary is in a gap reject that dated schedule rather than silently shift it. Derive appointment end by elapsed Duration on Instants, then compare with resolved working interval. An appointment crossing an offset change retains elapsed service duration. Examples for Europe/Vilnius: 2026-03-29 03:30 is invalid; 2026-10-25 03:30 chooses +03:00, i.e. 00:30Z. Exact end adjacency is allowed unless effective buffer occupancy conflicts.

EUR values normalize to two decimals with RoundingMode.HALF_UP, prohibit negative amounts, and compare numerically. Sum normalized base/add-on prices; retain a fee snapshot so catalog changes cannot alter history. No payment processing.

## Facade, events, observers, and simulated calendar (implemented S4)

BookingFacade exposes providers/services, advisory available(request), book, confirm, reschedule, cancel, complete, details, customer history and per-appointment event history. AppointmentAssembler resolves the repository catalogs and injected kind-to-creator map, then invokes Builder with the request's mode factory, decorator chain and Strategy. No concrete infrastructure is constructed in application code. Domain validation stays in existing creation, scheduling and State objects; no separate availability check authorizes a write.

AppointmentEvent is a domain record with stable repository-namespace/sequence ID, global sequence, per-appointment revision, type, captured Instant and immutable before/after Appointment snapshots. Before is absent only for RESERVED. These are immutable aggregates, not mutable live references. Events are recorded exactly once with each successful repository command. Failed commands append nothing. Current customer history remains distinct from append-only event history.

CommittedEventDispatcher uses an instance monitor and a cursor over the repository commit log instead of a destructive queue. One dispatcher/publisher/calendar combination must be shared by all facades for a repository lifetime. Facade commands and delivery serialize through that dispatcher; direct repository commands still serialize under the store lock, and dispatchPending() drains them in commit order. No background worker exists. Repository callbacks never perform delivery. Each dispatcher attempt invokes observers then the calendar, outside the repository mutation lock.

AppointmentEventPublisher snapshots subscribers and invokes them in registration order; duplicate registration is ignored and unsubscribe affects subsequent events. A set of attempted IDs prevents replay delivery. Each RuntimeException becomes a DeliveryFailure; remaining observers and the calendar still run. NotificationListener and AuditListener retain simulated immutable event snapshots. Reentrant publication and facade commands from listeners are rejected and isolated. Listeners must consume snapshots only, be quick, and never wait for another command thread. JVM fatal Errors are not treated as recoverable delivery failures.

BookingResult returns the committed appointment, its revision and this event's warnings. Dispatcher.failures() retains delivery failures including direct repository commands. No automatic delivery retry occurs. Calendar and observer failures never roll back committed domain operations. Successful command receipts are retained by caller-supplied command ID; retrying the same command returns its original result even after later changes. Reuse for different input rejects. BookingRequest equality includes its collaborator instances: retain the same request/immutable collaborators for retries. Failed commands do not consume an ID. Different command IDs represent new operations, including repeat reschedules. This is process-local retry suppression, not durable or distributed exactly-once delivery.

CalendarPort.synchronize(event) is a post-commit mirror. External busy/conflict information produces a typed warning and does not veto or undo a local reservation; available(request) reports local availability only. The local repository remains authoritative for collision prevention. This explicit advisory policy avoids an unreliable external check-then-write transaction. A blocked-key fixture simulates an external conflict. No external availability fetch or network request occurs.

ExternalCalendarAdapter translates lifecycle types into PUT/ACK/MOVE/DELETE/DONE, appointment IDs into legacy string keys, revisions into rN tokens, and Instants into exact epoch milliseconds with explicit business-zone IDs. Submillisecond timestamps and overflow are rejected, not rounded. SimulatedExternalCalendarClient.apply accepts primitive operation/key/start/end/zone/revision/event-key arguments; the extra event-key argument refines the planned API to support idempotency. Numeric errors map 400 to INVALID_TIMESTAMP, 409 to CONFLICT, and 503/unknown to UNAVAILABLE, retaining causes. The fake stores entries, rejects stale revisions, and remembers successful event keys. DELETE retains a tombstone to prevent stale resurrection; it represents an inactive entry. Failed events are not marked applied. No real calendar, email or SMS service exists.

Limits: log, receipts, deduplication sets and failure histories grow for this academic process lifetime; no pruning, durability, recovery, throughput or delivery-across-crash guarantee. Concurrent winner order is unspecified; committed event and revision order is deterministic. Reconstructing multiple independent dispatchers for one repository is unsupported composition. Main will wire the single shared instances only in authorized S5.

## Alternatives and limitations

One module and a single store lock are sufficient for the small demonstration; separate modules and distributed locks add cost without requirements. Repository atomic commands are chosen over application-side check-then-save. In-memory ordered dispatch is chosen over a broker/outbox database because durability is out of scope. Fixed clock demos avoid stale hard-coded future dates. No booking features or ports are instantiated in S0; Main will become the composition root when authorized.

## S5 console and composition (implemented October 26)

Main.create accepts InputStream, OutputStream, Clock and ZoneId. It constructs the immutable DemoCatalog, DemoSeed clock, repository, creator registration, one publisher/shared dispatcher/calendar and two observer instances, then injects ConsoleApplication. Main.main resolves appointease.zone and starts it. No domain/application/adaptor behavior was changed. ConsoleInput parses UTF-8 lines, strict dates/times and yes/no; ConsoleApplication owns menus, selections, mode/decorator/policy construction, rendering and calls to BookingFacade. Invalid choices and expected typed business errors return to menu. EOF unwinds any unfinished interaction without a write. It never reaches the repository. Read-only suppliers expose the two actual observer histories without infrastructure imports in presentation.

S5 refines the seed plan: three customers and the four planned category/provider/service pairs; DemoSeed books/confirms seed-ready-001 at 10:00 on the previous weekday through the normal facade. Its instance-local SetupClock starts before that booking, then permanently delegates to the injected runtime clock before the console is exposed. This gives an elapsed, legitimately confirmed appointment for immediate completion without importing arbitrary state or exposing time controls. The repository, facade and seed share the same clock and zone. There is one seed reservation, with two real seed events and simulated calendar writes. Future interactive dates are entered by the user; startup suggests the next weekday. No production fixed appointment dates.

Availability remains an advisory exact-slot query. Booking prints a decorator-produced quote and requires final confirmation; the facade revalidates before commit. Appointment kind filters services and the selected service's kind drives the existing creator map. Interactive IDs and command keys are UUIDs; @1 etc. are console-local shortcuts only. Rescheduling also asks for confirmation and leaves original capacity intact on rejection. All nine GoF implementations and domain dependency direction are preserved. UML: all six sources validated/rendered in S6 and synchronized again in S6.1.


## S6.1 reproducible dependency verification

Run `mvn clean verify` (or `mvn -Dtest=ArchitectureTest test` after compilation). ArchitectureTest checks all compiled production classes with JDK `jdeps -verbose:class -filter:none target/classes`, verifies class coverage, enforces the layer allowlist, and builds a graph keyed by exact Java package names, including nested classes and the root composition package. A depth-first active-path search detects direct or indirect cycles in every connected component. Only same-package edges and external JDK leaves are omitted from package-cycle traversal; no project package or edge is suppressed. Reports: target/architecture-jdeps.txt and target/architecture-packages.txt. Synthetic direct/indirect/disconnected cycles and a legal diamond test the detector. Source import checks also reject unused forbidden imports; presentation uses explicit application contracts to avoid importing the dispatcher through a wildcard. Existing static-field checks remain. This is compile-time dependency evidence, not reflection/runtime dependency inference.

## S7B desktop addendum (authorized October 27)

The preceding S7A boundary is historical. DesktopMain injects the same facade, customer list, DomainTime and observer suppliers into DesktopController. DesktopShell routes Overview, Appointments, New Appointment, Providers, Schedule and Activity. AppointmentDetailsView is reached through table selection, Overview rows or timeline entries. Presentation has no repository/infrastructure/root-package dependency. No domain, application, console, existing infrastructure or POM change was needed for S7B.

DesktopController handles field parsing, read-only filtering, navigation, immutable reviewed requests and facade commands. Quotes use the existing decorators; mode factories and strategies are the same collaborators used by the console. Local date/time parsing delegates DST decisions to DomainTime.resolve, and review displays the offset. Availability checks are advisory; book/reschedule always validate atomically in the existing facade/repository. PreparedBooking retains command ID, request and collaborator identity; PreparedMove retains the same key/start/strategy across retries. State eligibility is queried through detached immutable Appointment operations, not a second status/clock rule table. The actual facade operation rechecks at commit time.

Commands return committed BookingResult receipts. Delivery warnings remain successful reservations and are shown separately in the receipt/Activity; warning tests inject a failing calendar without changing production composition. Failed reschedules leave original capacity intact. Detail refresh and reloading destinations obtain fresh facade snapshots; there is no timer or background refresh. In-memory operations remain synchronous on the JavaFX thread for this small offline catalog. Activity reads actual simulated notification/audit suppliers, ordered by event sequence, with channel filtering and error recovery.

The dedicated Schedule is a time-ordered day timeline with individual entries for simultaneous bookings and a provider filter; its row spacing is not a duration scale. Overview retains its smaller proportional demo-hours agenda. Neither implies availability from blank space. Forms and toolbars wrap, the sidebar automatically collapses below 1000 logical pixels, and all content scrolls vertically. Screenshot and actual-window verification evidence is maintained in [S7B review](ui-review/S7B.md).
